# Mess Manager

A Flutter app for managing a shared mess/hostel: member dues, meal tracking,
expenses, and monthly billing — backed by a real [Serverpod](https://serverpod.dev)
server (Postgres-backed, typed end-to-end). Built with Clean Architecture,
`flutter_bloc` for state management, `go_router` for navigation, and
`get_it` for dependency injection.

## Tech stack

| Concern              | Package                                          |
|-----------------------|---------------------------------------------------|
| Backend               | `serverpod` (Postgres + Redis), `serverpod_auth_idp_server` |
| State management      | `flutter_bloc` (Bloc for auth, Cubit elsewhere)    |
| Dependency injection  | `get_it`                                           |
| Routing               | `go_router`                                        |
| Networking            | generated `mess_manager_server_client` (typed Serverpod client — no hand-written API calls) |
| Local session storage | `shared_preferences` (persists the auth token across app restarts) |
| Responsive UI         | `flutter_screenutil`                               |
| Charts                | `fl_chart`                                         |
| Images                | `cached_network_image`                             |
| Testing               | `flutter_test`, `bloc_test`, `mocktail`            |

## Backend

`mess_manager_server/` is a separate Dart workspace (not part of the
Flutter app's own package) with three parts:

- **`mess_manager_server_server/`** — the actual server. Endpoints live
  under `lib/src/`, one file per concern:
  - `auth/` — Serverpod's built-in email/password identity provider
    (registration, login, password reset, JWT sessions) plus a small
    email-sending hook (see `EMAIL_SETUP.md`).
  - `mess/` — `MessEndpoint` (create/join a mess by invite code),
    `MealEndpoint` (submit/approve meal counts), `ExpenseEndpoint`
    (market/shared expenses), `PaymentEndpoint` (deposits), and
    `DashboardEndpoint` (computed aggregates — balance cards, wallet,
    transactions, monthly summary — derived from the rows the other
    endpoints write, not stored separately). `mess_authorization.dart`
    holds the shared "is this caller a member / the manager" checks every
    one of these uses.
  - `profile/` — exposes Serverpod's user-profile editing.
  - Data models are `.spy.yaml` files under `lib/src/*/models/` —
    `serverpod generate` turns those into Dart classes, database tables,
    and the typed client the Flutter app imports.
- **`mess_manager_server_client/`** — generated by `serverpod generate`;
  the Flutter app depends on it directly (`mess_manager_server_client` in
  `pubspec.yaml`) instead of hand-writing HTTP calls.

Every feature's `data/datasources/*_remote_data_source.dart` in the
Flutter app calls into this client and translates Serverpod's typed
exceptions into this app's own `core/error/exceptions.dart` types, so the
rest of the app (usecases, Bloc/Cubit, UI) never touches Serverpod types
directly.

### Running the backend locally

You need Postgres and Redis running (either via the `docker-compose.yml`
Serverpod generates, or native installs — see each config file under
`mess_manager_server_server/config/` for the ports/credentials expected).
Real passwords go in `config/passwords.yaml`, which is git-ignored.

```bash
cd mess_manager_server/mess_manager_server_server
dart pub get
dart bin/main.dart --apply-migrations   # first run / after a schema change
```

Registration and password-reset codes are always logged to this console
(`[EmailIdp] Registration code (...): 123456`) — see `EMAIL_SETUP.md` in
that directory for wiring up real email delivery on top of that.

After changing a `.spy.yaml` model or adding an endpoint:

```bash
serverpod generate                        # regenerates server + client code
serverpod create-migration                # if a table's shape changed
dart bin/main.dart --apply-migrations --role maintenance
```

## Architecture

Each feature under `lib/features/` is a self-contained module split into
three layers, following Clean Architecture:

```
feature/
├── data/            # Concrete implementations — talks to the Serverpod client
│   ├── datasources/ #   *_remote_data_source.dart — calls the generated client,
│   │                 #   translates its exceptions into core/error/exceptions.dart
│   └── repositories/#   implements the domain repository contract
├── domain/          # Pure Dart, no Flutter/Serverpod imports — the business rules
│   ├── entities/    #   domain objects
│   ├── repositories/#   abstract contracts the data layer must satisfy
│   └── usecases/    #   one class per business operation, called by presentation
├── presentation/    # UI layer
│   ├── bloc/ or cubit/ #  state containers, call usecases
│   ├── pages/       #   screens
│   └── widgets/     #   feature-local, non-shared widgets
└── injection_container.dart   # registers this feature's dependencies into get_it
```

Dependency rule: `presentation → domain ← data`. The domain layer never
imports from `data` or `presentation`; `data` implements the interfaces
`domain` declares. This is what lets a usecase be unit-tested with a mocked
repository (see `test/features/*/`) without touching Flutter or the
network.

Cross-feature/shared code lives in `lib/core/` — nothing feature-specific
belongs there. Where one feature's data needs another's (e.g. the manager's
add-expense screen needs the real member list), the data source depends on
that other feature's repository/client calls directly rather than
duplicating a fetch.

## Onboarding flow

A session-less user lands on `WelcomeScreen` (`AppRoute.welcome`), not
straight on sign-in — the two things they can actually do (create a mess,
or join one with a pass code) are the first things they see:

1. **Create a Mess** / **Join with a Pass Code** opens a single-purpose
   bottom sheet (`mess_choice_sheet.dart`) for just that action — a mess
   name, or an invite code. This runs *before* an account exists
   (`PendingMessChoice` — no API call yet).
2. Once that resolves, a second sheet (`user_info_sheet.dart`) walks
   through registration in two steps, via `RegistrationCubit`:
   - **Account info**: name, email, phone, password → `startRegistration`
     sends a verification code to the email (logged to the server console
     in dev — see `EMAIL_SETUP.md` for real delivery).
   - **Verification code**: the 6-digit code → `verifyRegistrationCode`,
     then `finishRegistration` creates the account and the mess/membership
     together, so the account is never left without one.
3. `AuthBloc` emits `AuthAuthenticated`; the app lands on the dashboard.

`MessChoiceGate` (`AppRoute.messChoice`) is a separate, *locked* variant of
step 1 — the router redirects an already-authenticated session with no
mess membership there (e.g. an old account that predates this flow). It
attaches the mess to the existing session instead of carrying it through
registration.

## Routing & access control

Routes are declared as constants in `core/routes/app_route.dart` and wired
up in `core/routes/app_page.dart`, which also holds `_authRedirect` — a
single `GoRouter.redirect` that:
- sends unauthenticated users to `AppRoute.welcome` for any non-auth route,
- sends authenticated users away from the welcome/login routes,
- forces an authenticated-but-mess-less session to `AppRoute.messChoice`,
- blocks members from manager-only routes (`_managerOnlyRoutes`) even via
  direct/deep-link navigation.

`go_router_refresh_stream.dart` re-evaluates that redirect whenever
`AuthBloc`'s state changes, so a login/logout immediately reroutes without
a manual `context.go(...)` call at the call site — **except** when the
current location was reached via an imperative `context.push` (as splash's
push to `/welcome` is) rather than `context.go`: the refresh re-evaluates
against the last `go`-set location, not the pushed one, so it silently
no-ops. Every screen that can complete auth from on top of an imperative
push (e.g. `user_info_sheet.dart`) therefore calls `context.go(AppRoute.dashboard)`
explicitly on success instead of relying on the redirect alone — keep
doing that for any new one.

## State management conventions

- **`AuthBloc`** is the only app-wide Bloc — provided once in `main.dart`,
  above the router, and event-driven because auth has discrete triggers
  (login, finish registration, logout, session check).
- **`RegistrationCubit`** is deliberately separate from `AuthBloc` even
  though it's part of auth — it's transient, screen-local flow state (which
  step of sign-up you're on), not app-wide session state.
- Every other feature uses a **Cubit** — simpler surface for
  screen-scoped state that's mostly "load / react to a filter change."
- `BlocBuilder`/`BlocListener` calls use `buildWhen`/`listenWhen` where a
  widget only cares about one field of a larger state, to avoid rebuilding
  on unrelated state changes.

## Dependency injection

`core/di/service_locator.dart` is the single entrypoint called from
`main()`. It registers the shared Serverpod `Client` (and its persistent
auth-token manager) first, then delegates to each feature's own
`injection_container.dart` to register that feature's data sources,
repositories, usecases, and Bloc/Cubit — so a feature's DI wiring lives
next to the feature itself, not in one growing global file.

## Testing

Two layers, deliberately separate:

- **Usecase tests** (`test/features/*/`) mock the domain repository with
  `mocktail` and assert the usecase forwards params and surfaces
  `Result`/`Failure` correctly — no Flutter or network involved, which is
  only possible because usecases depend on the abstract repository, not
  its implementation. Run with `flutter test` — hermetic, no server
  needed.
- **Integration scripts** (`dev_scripts/*.dart`) drive the real
  repository layer against a live backend — register real accounts,
  create a mess, submit/approve meals, record expenses/payments, and
  assert the numbers that come back. They live outside `test/` on purpose
  so a plain `flutter test` never picks them up (they need Postgres/Redis
  and a running server); run one explicitly once the backend is up:
  ```bash
  flutter test dev_scripts/expenses_flow_test.dart
  ```
  Each script reads the emailed verification code straight from the
  server's console log, so point its `_serverLogPath` constant at
  wherever you redirected `dart bin/main.dart`'s output.

Run everything hermetic:

```bash
flutter pub get
flutter analyze
flutter test
```

## Getting started

1. Start the backend (see "Running the backend locally" above) — Postgres
   and Redis need to be reachable first.
2. Then:
   ```bash
   flutter pub get
   flutter run
   ```

`lib/core/network/serverpod_client.dart` hardcodes `http://localhost:8080/`
as the server URL — that works for iOS simulators and desktop, but the
Android emulator needs `10.0.2.2` instead, and a real device needs your
machine's LAN IP. Switch that constant (or make it a build-time flag) to
match whichever target you're running on.
